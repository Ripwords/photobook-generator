# Native completion notification for `analyze_folder`

## What was built

- `src-tauri/Cargo.toml`: added `tauri-plugin-notification = "2"` (resolved to 2.3.3).
- `src-tauri/src/lib.rs`: added `.plugin(tauri_plugin_notification::init())`.
- `src-tauri/capabilities/default.json`: added `"notification:default"` to the
  permissions array, matching the `dialog:default` / `fs:default` pattern
  already used for the other plugins in this file.
- `src-tauri/src/commands.rs`:
  - `NOTIFY_MIN_ELAPSED: Duration = Duration::from_secs(10)` — named
    threshold constant.
  - `pub(crate) fn should_notify(elapsed: Duration, window_focused: bool) -> bool`
    — pure decision: `!window_focused && elapsed >= NOTIFY_MIN_ELAPSED`. Both
    conditions are required.
  - `pub(crate) fn count_keepers(photos: &[serde_json::Value]) -> usize` —
    ports `keepers()` from `app/types/features.ts` (drop `isUtility`, keep
    the sharpest photo per `nearDupCluster`, tie-broken by
    `aestheticPct`) into Rust. This did **not** already exist on the Rust
    side despite the brief's phrasing ("the command already computes those
    counts") — `total`/`cached`/`failed` were already computed, but
    "keepers" is frontend-only logic. I ported it rather than assume; noted
    here since it's a duplication risk if `keepers()` in `features.ts` ever
    changes without a matching change here.
  - `analyze_folder` now: times itself with `Instant::now()`/`.elapsed()`;
    after `finalize_photos`, resolves window focus via
    `app.get_webview_window("main")` (the label is fixed — `capabilities/default.json`
    declares `"windows": ["main"]` and `tauri.conf.json`'s single window has
    no explicit `label`, so it defaults to `"main"` — this is reliable, not
    a guess); calls `should_notify`; on `true`, calls
    `app.notification().builder().title("Analysis complete").body(...).show()`.
    Any `Err` (denied permission, plugin failure, or a missing window
    handle) is `log::warn!`'d and swallowed — never propagated — so
    `analyze_folder`'s `Result` is unaffected. If focus can't be determined
    at all, it defaults to "focused" (`true`), i.e. it *suppresses* rather
    than risks a spurious notification.

(false), **exactly at threshold+unfocused** (true — the boundary), just over

## Live verification

Built a real release `.app` bundle (`bun x tauri build --bundles app`,
`bundle.identifier = com.jiajingteoh.photobook`, `productName = PhotobookGen`).

**What I could confirm directly:**
- The plugin wires up and compiles cleanly against `tauri = "2.11.3"`.
- `app.notification().permission_state()` reports `Granted` and `.show()`
  returns `Ok(()))` — the call succeeds from Rust's point of view.
- Running the *exact same* `.show()` call as a raw, unbundled test binary
  (`cargo test`) is **silently swallowed by macOS**: `log show --predicate
  'process == "usernoted"'` showed `Denying message 3 from connection
  <LegacyConnection identifier: com.apple.Terminal ...>` — the underlying
  crate (`mac-notification-sys`, via `notify-rust`) uses the deprecated
  `NSUserNotificationCenter` API and impersonates `com.apple.Terminal`'s
  bundle identity when the process isn't inside a real `.app` bundle, and
  that borrowed identity had no notification permission on this machine.
  `.show()` still returned `Ok(())` despite the OS dropping it — proof that
  `Ok` from this API is not proof of delivery.
- Copying the same probe binary into the real bundled `.app`'s
  `Contents/MacOS/` (so it runs under the app's real `Info.plist`/bundle id)
  changed the outcome: macOS correctly recognised the app by its real name
  and produced a genuine, visible system permission prompt — confirmed via
  screenshot: **`"PhotobookGen" Notifications — Notifications may include
  alerts, sounds and icon badges.`** This is the real, first-run permission
  dialog for the app, exactly as production would show it.

**What I could not confirm:** clicking "Allow" and then seeing the actual
"Analysis complete" banner render. `osascript`/System Events UI scripting is
not granted Accessibility access in this shell (`osascript is not allowed
assistive access (-1728)`), so I could not click the system prompt
programmatically, and I deliberately did not attempt blind pixel-coordinate
clicks against the user's live desktop (which had other applications open).
I did not run the full `analyze_folder` pipeline against padded photo
fixtures end-to-end either, given the remaining time budget, since the
open question was specifically about OS-level notification delivery, not
about whether `analyze_folder` computes its counts correctly (that part is
unit-tested and already exercised by `sidecar_worker_pool.rs`).

**Bottom line:** the code path is correct and reaches the OS in the right
shape (right bundle identity, right API, permission prompt fires), but
whether a granted permission actually produces a visible banner for this
specific plugin/macOS 15 combination is unverified — pending a manual click
of "Allow" by someone with an interactive session on this machine.

## Concerns / follow-ups

- `count_keepers` duplicates `keepers()` from `app/types/features.ts` by
  necessity (no Rust/TS boundary to share it through). If that TS function's
  culling rule changes, this Rust copy needs a matching change or the
  notification body will silently drift from what the UI shows.
- The underlying macOS notification pathway for unbundled processes falls
  back to impersonating Terminal's identity and gets silently denied. This
  is invisible to `analyze_folder` (by design — failure is swallowed), but
  worth knowing if "notifications never show up" is reported during `tauri
  dev`: dev-mode processes are not real `.app` bundles either, so the same
  Terminal-spoofing/denial may apply there. Only a `tauri build` bundle (or
  a codesigned/notarized one for actual distribution) reliably gets its own
  notification identity and permission prompt.
