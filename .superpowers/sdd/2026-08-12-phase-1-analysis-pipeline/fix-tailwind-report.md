# Fix: Tailwind / @nuxt/ui styling never loads

## Root cause

`nuxt.config.ts` had no `css:` entry, so `.nuxt/ui.css` (generated by the
`@nuxt/ui` module) and Tailwind itself were never imported into the app
bundle. Every utility class in every template was inert; the app rendered
in the browser default serif font with no spacing.

## Changes

1. **`app/assets/css/main.css`** (new file) — minimal, matching the
   reference project's pattern but deliberately without Luna's theme block
   (no Geist fonts, no monochrome `--ui-primary` overrides — this project
   has no visual design decisions yet):

   ```css
   @import "tailwindcss";
   @import "@nuxt/ui";
   ```

2. **`nuxt.config.ts`** — added one line, nothing else touched:

   ```diff
      compatibilityDate: "2026-08-12",
   +  css: ["~/assets/css/main.css"],
      vite: {
   ```

3. **`tests/scaffold.test.ts`** — replaced the tautological test (see below).

## Why the old test was worthless

The old test asserted `config.ssr === false` and `config.ignore` contains a
string — both hardcoded in the same commit as the config, so the test just
echoed the config back to itself. It never touched CSS at all, so it could
not have caught this defect regardless.

## Attempt 1: real component mount (preferred option) — ruled out, with evidence

I installed `@nuxt/test-utils`, `@vue/test-utils`, `happy-dom` and set up
`vitest.nuxt.config.ts` (mirroring luna-ultra-desktop's `environment: "nuxt"`
setup), then wrote a test mounting `app/pages/index.vue` via `mountSuspended`
and asserting `getComputedStyle(h1Element).fontWeight === "600"` etc.

Result **with the fix already applied** (should have passed if this
approach worked):

```
FAIL  tests/nuxt/css.test.ts > tailwind css wiring > actually applies compiled Tailwind styles to the index page heading
AssertionError: expected '' to be '600'
```

`mountSuspended` under the `nuxt` vitest environment (happy-dom) does not
inject Vite-processed CSS into the document — there is no `<style>`/`<link>`
tag appended, so `getComputedStyle` always reports empty/default values
regardless of whether the css wiring is correct. This test would be red in
both the buggy and fixed state, i.e. it is not a valid red→green check, so
I discarded it (deleted `tests/nuxt/css.test.ts`, `vitest.nuxt.config.ts`,
and removed the three added devDependencies via `bun remove`, then restored
`bun.lock` with `git checkout -- bun.lock` and re-ran `bun install` to sync
`node_modules`). `package.json`/`bun.lock` are unchanged from before this
task (`git diff package.json` is empty).

## Attempt 2: cross-check test (fallback option, shipped)

`tests/scaffold.test.ts` now has a third test that:
1. Asserts `nuxt.config.ts` declares a non-empty `css` array.
2. Resolves each entry against the `app/` directory (respecting the `~`
   alias) and asserts the file actually exists on disk.
3. Reads the file contents and asserts it imports both `"tailwindcss"` and
   `"@nuxt/ui"`.

This is a real cross-check (config → filesystem → file contents), not an
echo of a single hardcoded value.

## Things I'm unsure about / flagging

- The cross-check test is deliberately weaker than a true rendered-style
  assertion, per the task's own fallback allowance — it can't catch a case
  where `main.css` exists, is imported correctly, but Tailwind itself fails
  to process some class at runtime for an unrelated reason (e.g. a content
  glob misconfiguration). Given `@nuxt/ui`'s Tailwind v4 Vite plugin needs
  no extra `content:` config in this setup (confirmed via the live dev
  server output containing compiled `.p-8`/`.font-semibold` rules), I
  don't think this is a live risk today, but it's worth knowing the test's
  blind spot.
- I did not commit anything — no explicit instruction to commit was given
  in the task, and the last five commits on this branch are unrelated
  template-library work from a different task stream. Let me know if you
  want this committed as `fix(ui): wire up Tailwind/@nuxt/ui stylesheet`.
